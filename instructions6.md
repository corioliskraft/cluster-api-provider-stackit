# Instructions: Add Cluster API Core RBAC Aggregation

## Goal

Add Cluster API core RBAC aggregation for the STACKIT infrastructure provider.

The CRDs already carry the Cluster API contract label
`cluster.x-k8s.io/v1beta2: v1alpha1`, but the provider also has to ship
aggregated RBAC so the Cluster API core manager can operate on this provider's
infrastructure resources.

Add a `ClusterRole` labeled:

```yaml
cluster.x-k8s.io/aggregate-to-manager: "true"
```

for these resources in API group `infrastructure.cluster.x-k8s.io`:

- `stackitclusters`
- `stackitclustertemplates`
- `stackitmachines`
- `stackitmachinetemplates`

This should allow Cluster API core controllers to manage owner references,
labels, and ClusterClass-generated infrastructure resources correctly.

## What RBAC Aggregation Means

Kubernetes `ClusterRole` aggregation lets one `ClusterRole` collect rules from
other `ClusterRole` objects using label selectors. The collecting role has an
`aggregationRule`; Kubernetes continuously updates its effective `rules` from
all matching roles.

Cluster API core uses this pattern for its manager permissions. In the local
Cluster API checkout:

```text
/Users/c.voigt/go/src/tangled.org/voigt.tngl.sh/cluster-api/config/rbac/aggregated_role.yaml
```

the `aggregated-manager-role` selects roles with:

```yaml
cluster.x-k8s.io/aggregate-to-manager: "true"
```

Cluster API's manager `ClusterRoleBinding` is patched to bind the manager
service account to that aggregated role:

```text
/Users/c.voigt/go/src/tangled.org/voigt.tngl.sh/cluster-api/config/default/manager_role_aggregation_patch.yaml
```

Infrastructure providers must therefore ship additional `ClusterRole` objects
with the aggregation label. Those roles are not for this provider's controller
manager. They grant the Cluster API core manager the permissions it needs for
provider-specific custom resources.

This matters because CAPI core controllers update metadata on infrastructure
objects, create resources from templates, and manage resources generated by
ClusterClass/topology. Without the aggregated role, CAPI core can fail with RBAC
errors even though this provider's own manager has sufficient permissions.

## Implementation Plan

1. Create a new static RBAC manifest under `config/rbac`.

   Suggested file name:

   ```text
   config/rbac/capi_manager_aggregation_role.yaml
   ```

   The role should be a `ClusterRole`, not a namespaced `Role`.

   Suggested role name before kustomize name prefixing:

   ```text
   capi-manager-aggregation-role
   ```

   Use a clear name, but avoid reusing `manager-role`; this role is for CAPI
   core aggregation, not for the STACKIT provider manager itself.

2. Add the required aggregation label:

   ```yaml
   metadata:
     labels:
       cluster.x-k8s.io/aggregate-to-manager: "true"
   ```

   It is fine to also include the repo's usual static labels:

   ```yaml
   app.kubernetes.io/name: cluster-api-provider-stackit
   app.kubernetes.io/managed-by: kustomize
   ```

   Preserve the aggregation label exactly. The key and string value are what the
   CAPI aggregated manager role selects.

3. Add RBAC rules for the provider resources.

   Use the provider API group:

   ```yaml
   apiGroups:
   - infrastructure.cluster.x-k8s.io
   ```

   Use these resources:

   ```yaml
   resources:
   - stackitclusters
   - stackitclustertemplates
   - stackitmachines
   - stackitmachinetemplates
   ```

   Use these verbs:

   ```yaml
   verbs:
   - create
   - delete
   - get
   - list
   - patch
   - update
   - watch
   ```

   Do not include `/status` or `/finalizers` unless careful research in the
   Cluster API local checkout proves CAPI core needs those subresources. The
   documented provider contract examples grant read/write on the main resources
   for CAPI metadata and topology management. Status and finalizers are owned by
   this infrastructure provider's controller.

4. Wire the manifest into `config/rbac/kustomization.yaml`.

   Add the new file to the `resources:` list. Place it close to `role.yaml` or
   near the other project RBAC helpers. Keep comments clear that this role is
   consumed by Cluster API core via aggregation and is not the provider manager's
   own runtime role.

5. Do not edit generated CRDs or generated controller RBAC unless regeneration
   requires it.

   This change is expected to be a static manifest addition. It should not need:

   ```sh
   make manifests
   make generate
   ```

   `config/rbac/role.yaml` is generated by controller-gen from kubebuilder RBAC
   markers and grants permissions to the STACKIT provider manager. The CAPI
   aggregation role grants permissions to a different manager, so it should be a
   separate static YAML file.

6. Confirm the install output includes the new role.

   Run:

   ```sh
   kubectl kustomize config/default | rg -n "aggregate-to-manager|capi-manager-aggregation|stackitclusters|stackitmachinetemplates"
   ```

   If `kubectl kustomize` is not available in the environment, use:

   ```sh
   kustomize build config/default | rg -n "aggregate-to-manager|capi-manager-aggregation|stackitclusters|stackitmachinetemplates"
   ```

   Expected result:

   - there is a `ClusterRole` containing
     `cluster.x-k8s.io/aggregate-to-manager: "true"`
   - the role contains all four STACKIT resources
   - the role grants `create`, `delete`, `get`, `list`, `patch`, `update`,
     `watch`

7. Check whether kustomize name prefixing affects the role name.

   `config/default/kustomization.yaml` applies:

   ```yaml
   namePrefix: cluster-api-provider-stackit-
   ```

   That is acceptable for this role because CAPI selects it by label, not by
   name. The important part is that the aggregation label survives kustomize.

8. Run manifest-rendering validation.

   At minimum:

   ```sh
   kubectl kustomize config/default >/tmp/capi-stackit-install.yaml
   rg -n "aggregate-to-manager|stackitclusters|stackitmachines|stackitclustertemplates|stackitmachinetemplates" /tmp/capi-stackit-install.yaml
   ```

   If the repo has a release/clusterctl bundle target that is normally used for
   packaging, run the appropriate target and confirm the new RBAC file is
   included in the generated install assets. Prefer existing Makefile targets
   and docs over inventing a new packaging path.

9. Run behavioral RBAC aggregation validation.

   Manifest rendering proves the YAML exists, but it does not prove Kubernetes
   actually aggregates the role into CAPI core's effective manager permissions.
   Validate this behavior against a disposable local cluster. Use an isolated
   kind cluster; do not run this against a shared or production cluster.

   Create a temporary cluster:

   ```sh
   kind create cluster --name capi-stackit-rbac-aggregation
   kubectl config use-context kind-capi-stackit-rbac-aggregation
   ```

   Install Cluster API core from the local checkout, then install this
   provider's rendered manifests. Prefer the local checkout over remote release
   artifacts:

   ```sh
   kubectl kustomize /Users/c.voigt/go/src/tangled.org/voigt.tngl.sh/cluster-api/config/default \
     | kubectl apply -f -

   kubectl kustomize config/default \
     | kubectl apply -f -
   ```

   Wait until RBAC aggregation has reconciled. Aggregation is asynchronous; use
   polling rather than assuming it is immediate:

   ```sh
   kubectl get clusterrole aggregated-manager-role -o yaml \
     | rg -n "stackitclusters|stackitmachines|stackitclustertemplates|stackitmachinetemplates"
   ```

   If the local Cluster API install prefixes the aggregated role name, inspect
   the installed `ClusterRoleBinding` for the CAPI manager service account and
   use its `roleRef.name` instead of hard-coding `aggregated-manager-role`.

   Then verify effective permissions with Kubernetes authorization checks. Use
   the actual CAPI manager service account installed by the local Cluster API
   manifests. If the service account name differs, discover it with:

   ```sh
   kubectl -n capi-system get serviceaccounts
   kubectl get clusterrolebinding -o yaml | rg -n "capi-system|aggregated-manager-role|manager"
   ```

   Run `kubectl auth can-i` for every required resource and verb:

   ```sh
   for resource in stackitclusters stackitclustertemplates stackitmachines stackitmachinetemplates; do
     for verb in create delete get list patch update watch; do
       kubectl auth can-i "${verb}" "${resource}.infrastructure.cluster.x-k8s.io" \
         --as system:serviceaccount:capi-system:capi-controller-manager
     done
   done
   ```

   Every command should print `yes`. If any command prints `no`, the aggregation
   role is incomplete, the role was not selected by label, or the wrong service
   account/aggregated role name was used for validation.

   Also verify that status/finalizer subresources were not accidentally granted
   unless the implementation intentionally added them with documented evidence:

   ```sh
   kubectl auth can-i update stackitclusters/status.infrastructure.cluster.x-k8s.io \
     --as system:serviceaccount:capi-system:capi-controller-manager
   kubectl auth can-i update stackitmachines/finalizers.infrastructure.cluster.x-k8s.io \
     --as system:serviceaccount:capi-system:capi-controller-manager
   ```

   These checks should normally print `no`.

   Clean up the temporary cluster after validation:

   ```sh
   kind delete cluster --name capi-stackit-rbac-aggregation
   ```

10. Consider adding a small test only if this repository already has manifest
   rendering tests.

   Do not add a heavyweight test framework just for this. A static RBAC manifest
   plus the kind-based RBAC aggregation validation above is enough unless the
   existing test suite has a natural place for RBAC manifest assertions.

## Expected Manifest Shape

The final role should be equivalent to this, adjusted only for naming or
existing label conventions:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  labels:
    app.kubernetes.io/name: cluster-api-provider-stackit
    app.kubernetes.io/managed-by: kustomize
    cluster.x-k8s.io/aggregate-to-manager: "true"
  name: capi-manager-aggregation-role
rules:
- apiGroups:
  - infrastructure.cluster.x-k8s.io
  resources:
  - stackitclusters
  - stackitclustertemplates
  - stackitmachines
  - stackitmachinetemplates
  verbs:
  - create
  - delete
  - get
  - list
  - patch
  - update
  - watch
```
